# 多样性实验一：多张C0表取最小（2026-10-22）

## 设计

从渐进方案的E133（`outputs/progressive_recipe_20261020/train/checkpoint-133.pt`）完整恢复，沿原学习率曲线续训30轮到E163，两个分支同时运行、各16个worker（入口 `scripts/run_recipe_continuation.py`，git分支 `codex/recipe-diversity`）：

- ctrl：不改动；
- multi_c0：`rl_multi_c0_bound=True`，RL的Target上界改为对所有精算路线（Anchor、Expert、refresh的基准与候选）的C0表按整条路线取最小。只影响有C0刷新的大J batch，不增加Gurobi调用。

ctrl前6个batch与原训练E134逐项一致。在validation2000（2000例，完整POMO，不增强）上每3轮评测一次，以E133为配对基线（复测17.70301，与原值一致）。结果在 `outputs/recipe_diversity_20261022/select_{ctrl,multi_c0}_validation2000/`。

训练日志：multi_c0每实例平均使用2.08张额外C0表，但Target上界平均只收紧0.32%（相对上界本身40–100%的松弛，可以忽略）；改进Expert比例（36.6%对36.3%）和Target优于Expert的比例几乎相同。

多样性诊断（200例，E163）：路线重合度 ctrl/multi_c0 在J20为0.638/0.642、J60为0.670/0.677、J100为0.622/0.622（G200为0.476/0.546/0.529），没有改善；续训本身还让J100的重合度从E150的0.592升到0.622。

## 结论

多张C0表取最小几乎没有收紧上界：这些表都来自Anchor/Expert附近的少数路线，对多样的Target路线帮助很小，因此既没有减轻塌缩，也没有改善成绩，后期反而略差。不采纳。E133之后继续用同一配方训练也没有收益，并会进一步加剧塌缩。下一步应从IL侧处理多样性（按起点的标签、降低IL强度）。
